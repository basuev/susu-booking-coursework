# ADR-0004: Transactional outbox для надежной публикации событий

**Статус**: принято

## Контекст

Сервис должен сохранить изменение бронирования и опубликовать
соответствующее доменное событие так, чтобы либо оба действия удались,
либо ни одно из них. Наивный «публикуем после коммита» дает «потерянное
событие» при падении между коммитом и публикацией; «публикуем, потом
коммитим» дает «фантомное событие» при откате.

Альтернативы:

- Двухфазный коммит (XA) между PostgreSQL и NATS — ни одна сторона его
  толком не поддерживает; операционно болезненно.
- Change Data Capture (Debezium, pg logical decoding), читающий таблицу
  `booking` напрямую — возможно, но тяжеловесно: отдельный коннектор
  Debezium, snapshot'ы, управление схемами, плюс cdc-стрим имеет форму
  строки, а не доменного события, так что downstream-маппер все равно
  нужен.
- Best-effort публикация с повтором при следующем запросе — протекает
  доменная семантика в обработку запросов и события все равно теряются,
  если процесс умер.

## Решение

Использовать паттерн «transactional outbox». В той же SQL-транзакции,
которая записывает агрегат, добавлять строку на каждое доменное событие
в `outbox_message` (статус `PENDING`, json-payload, счетчики попыток).
Фоновый worker пакетами забирает «pending»-строки, публикует их в NATS
JetStream и помечает как `PUBLISHED`. При сбоях растет `attempt_count`;
строки, превысившие `OUTBOX_MAX_ATTEMPTS`, переходят в `DLQ`.

Шаг «select pending» использует
`UPDATE outbox_message SET status='IN_PROGRESS' WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING ...`,
поэтому захват и lease происходят атомарно — нет промежутка
read/commit/process, в котором второй worker мог бы увидеть ту же строку.

## Последствия

- Доменные события гарантированно будут опубликованы в итоге, пока БД
  держит строку.
- Публикация at-least-once: при повторах возможна дублированная
  доставка. Consumer'ы обязаны быть идемпотентны (projector делает
  upsert по booking id; внешним consumer'ам понадобится собственная
  дедупликация).
- Лишняя таблица в миграциях, лишний worker в эксплуатации.
- Добавляет задержку публикации, ограниченную сверху `OUTBOX_INTERVAL`
  (по умолчанию 500ms). Это приемлемо для модели чтения; не подходит,
  если нужен синхронный внешний side-effect до возврата gRPC-ответа.
- Строки в `DLQ` требуют ручного разбора; никаких автоматических
  повторов для них нет.
