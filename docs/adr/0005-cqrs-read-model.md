# ADR-0005: «CQRS»-проекция для ListBookings

**Статус**: принято

## Контекст

`ListBookings` должен фильтровать по гостю, статусу и диапазону дат
заезда, с пагинацией. Отдача этого запроса напрямую из модели записи
означает join `booking` и `booking_offer_snapshot`, что усложняет запрос,
привязывает производительность списка к решениям по схеме write-стороны
и делает добавление новых измерений фильтрации инвазивным (каждое
изменение трогает репозиторий агрегата).

Модель записи оптимизирована под FSM-переходы: строки обновляются
in-place под оптимистической блокировкой, история только дописывается, а
snapshot предложения апсертится при создании. Ни одна из этих форм не
идеальна для фильтрации или пагинации по многим гостям.

## Решение

Разделить модель чтения и модель записи. Агрегат хранить в `booking` /
`booking_offer_snapshot` / `booking_status_history`. Поддерживать
денормализованную модель чтения `booking_projection`, наполняемую по
доменным событиям. `ListBookings` читает только из проекции; `GetBooking`
по-прежнему читает из модели записи (ей нужно самое свежее состояние и
полная история).

Проекцию наполняет worker, подписанный на `booking-events` через
durable-consumer'а. Каждое событие триггерит идемпотентный upsert по
ключу booking id.

## Последствия

- Запросы списка попадают в плоскую узкую таблицу — ее легко
  индексировать под активные измерения фильтрации.
- Проекция согласована в конечном счете. Хвостовая задержка ограничена
  сверху интервалом outbox плюс временем доставки в NATS. Задокументирован
  как известный компромисс; клиенты, которым нужно самое свежее
  состояние одного бронирования, используют `GetBooking`.
- Два пути записи: агрегат в модель записи (синхронно) и событие в
  проекцию (асинхронно). Асинхронный путь идемпотентен и устойчив к
  дубликатам из outbox.
- Лишняя таблица в миграциях и лишний worker в эксплуатации.
- Схема чтения может развиваться независимо — добавление нового фильтра
  сводится к миграции плюс обновлению поля в projector'е, без изменений
  в домене.
