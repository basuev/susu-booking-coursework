# ADR-0002: PostgreSQL как основное хранилище через database/sql + pgx

**Статус**: принято

## Контекст

Сервису нужно надежное хранилище со строгой транзакционной семантикой
(паттерн «transactional outbox» требует, чтобы состояние агрегата и
строка outbox коммитились атомарно). Также нужны оптимистическая
блокировка, частичные индексы для outbox-worker'а и JSON-payload'ы для
тел событий.

Рассмотренные альтернативы:

- Документная БД (MongoDB и т. п.) — нет мультитабличных транзакций,
  пришлось бы использовать другой подход к outbox (например, «event
  sourcing»).
- Key-value хранилище — та же проблема, плюс теряются индексы для
  `List`.
- Прямой `pgxpool` — дает pgx-native возможности (`CopyFrom`, нативные
  типы), но привязывает каждый адаптер к pgx и лишает абстракции
  драйвера `*sql.DB` и хуков stdlib.

## Решение

Использовать PostgreSQL 16 как основное хранилище. Доступ — через
`database/sql` с драйвером `github.com/jackc/pgx/v5/stdlib`. Транзакции
проходят через порт `TxManager`; `BookingRepo.Save` принимает
`context.Context`, который может нести `*sql.Tx`, поэтому один и тот же
метод работает как внутри окружающей транзакции, так и без нее.

## Последствия

- Все hot-path операции выполняются в одной SQL-транзакции — агрегат,
  snapshot предложения, история статусов, идемпотентность, outbox.
- Миграции — SQL-файлы golang-migrate, встраиваемые через `embed.FS` и
  применяемые при старте.
- Пул соединений настраивается через env (`DB_MAX_OPEN_CONNS`,
  `DB_MAX_IDLE_CONNS`, `DB_CONN_MAX_LIFETIME`).
- Адаптеры можно тестировать с настоящим postgres через testcontainers
  (`-tags=integration`) без специфичного для pgx мокирования.
- Отказ от pgx batch / `CopyFrom` приемлем на текущем масштабе; если
  объем записи существенно вырастет, отдельные hot-path можно перевести
  на нативный pgx через аксессор `Raw` у драйвера, не меняя расслоения.
