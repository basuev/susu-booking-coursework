# ADR-0003: NATS JetStream для доменных событий

**Статус**: принято

## Контекст

Сервис эмитит четыре доменных события
(`BookingCreated`/`Cancelled`/`Approved`/`Rejected`), которые нужно
доставлять как минимум одному внутрипроцессному consumer'у (projector
модели чтения), а в production — еще и downstream-сервисам (уведомления,
биллинг, аналитика), которые выходят за рамки данной курсовой работы.

Требования:

- Доставка at-least-once; projector идемпотентен, поэтому дубли
  допустимы.
- Персистентность, чтобы consumer'ы могли переподключиться и проиграть
  события заново.
- Durable-consumer'ы с явным ack.
- Один бинарь для эксплуатации; никакого zookeeper'а, никакого реестра
  схем.

Альтернативы:

- Kafka — хорошо подходит, но операционно тяжела для развертывания
  одного сервиса в курсовой. Управление схемами + партиции + zookeeper /
  KRaft — это больше, чем здесь нужно.
- RabbitMQ — подходит для маршрутизации, но стримы JetStream «из
  коробки» дают упорядочивание по subject и replay без топологии
  exchange/queue.
- Plain NATS (core) — только at-most-once. Теряет гарантии доставки при
  рестарте consumer'а.

## Решение

Использовать NATS JetStream. Один стрим `booking-events` покрывает все
subject'ы `booking.created`, `booking.cancelled`, `booking.approved`,
`booking.rejected`. Projector привязывает durable pull-consumer'а.
Управление соединением живет в `internal/adapter/natsx`.

## Последствия

- Один контейнер в `docker-compose.yml`, одна runtime-зависимость.
- Durable-consumer'ы переживают рестарты; при старте projector
  доигрывает события с последнего ack.
- Межсервисную маршрутизацию позже можно добавить через subject'ы или
  второй стрим, не меняя код publisher'а.
- Схема обеспечивается Go-типами и json-тегами; центрального реестра
  нет. Это приемлемо для конфигурации с одним publisher'ом и одним
  consumer'ом.
- Если проекту когда-нибудь понадобится строгое упорядочивание между
  многими партициями или log compaction по ключу, это решение следует
  пересмотреть.
